# Limits and automatic behaviour

Every cap, allowance, timer, cache and thing Movie Night does by itself, in
one place. If something stops working "for no reason", or works differently
from what you expected, look here first.

**The owner's rule: the whole app, no usage limits.** Nobody is capped in
how much they use Movie Night: no daily, hourly or per-minute counts on
searches, AI calls or anything else, and no install-wide allowances of our
own. If limits are ever set, they will be set by the owner **per person**,
not for the whole install. The only exception is the one the owner chose
to keep, listed next ([Limits the owner keeps](#limits-the-owner-keeps)).
What remains below is a timer
or a cache, or one of the [technical limits](#technical-limits-not-usage-caps):
a security measure, a size that keeps the app working, or a limit set by an
outside service that Movie Night can't raise. Each of Movie Night's own is a
setting (an outside service's is changed at that service, and the
database's whole-number range is the type of its columns), and each says in
plain words when it is hit.

How to read the tables:

- **Where it's set** says how to change it. An `ENV_VAR` goes in `.env`
  (then `docker compose up -d`). "hard-coded" means it is a value in the code
  (file and line given); changing it is a code change.
- **Install-wide** means shared by everyone on this Movie Night. Nothing
  here is per person unless it says so.
- **Time zones:** the background jobs, Home's morning/noon/night rows, digest
  periods and a watch date given without a time use `TIMEZONE` (default
  `America/New_York`).
- File and line references are for this version of the code; the comment at
  each one says the same thing in short.

## The ones most likely to surprise you

1. **Nothing in the database is purged on a schedule.** The host backs the
   database up every night and keeps copies for about 6 months, so what is
   deleted, a deleted account included, stays in the backups that long (see
   [Data kept, and data deleted](#data-kept-and-data-deleted)). (The logs
   are rotated and name nobody: see Logs there.)

## Background jobs

They run inside the web process (`app/jobs.py`), at times in `TIMEZONE`.
`RUN_JOBS=false` turns them all off. APScheduler keeps the schedule in
memory, so a run due while the app was down is never made by itself: for
the **digests** Movie Night keeps which period each kind was last run for
in full (`app_settings` keys `digest_done:week`, `:month`, `:year`) and a
catch-up, 4 min 20 s after it starts and then **every hour**, makes any
latest run that isn't done (the log says so, WARNING "week digests not all
sent (due while Movie Night wasn't running, or a send failed); sending them
now"); each digest is still sent once (its `sent_at`). A run in which a
digest couldn't be built or sent (the SMTP server down, a model error) is
not recorded as done (WARNING "week digests: 1 couldn't be built or sent;
tried again at the next hourly catch-up"), so the catch-up tries the
unsent ones each hour until all have gone out or the next period's run is
due; a digest of the period before that never went out then stays unsent.
Each digest goes out **at most once** (`app/services/digest.py`, `send`;
`app/clients/mailer.py`): its send is recorded (`digests.sending_since`)
before the SMTP call. A **clear failure** (no connection, TLS or sign-in
failed, a refusal with an error code) is tried again, at most
`DIGEST_SEND_TRIES` (3) times per person and period (`digests.send_tries`;
"Send it to me now" isn't counted), then given up on for that period with
an ERROR ("week digest 5 for user 12 not sent after 3 tries; not tried
again for this period"), and the run counts as done. A send whose **fate
is unknown** counts as sent, with a WARNING, and is never repeated: the
connection broke after the email was handed over (from DATA on, before the
server answered: a timeout, a hang-up), or a send started and never
reported back (the app stopped midway, or the database write after it
failed). A failure after the server's 250 (its answer to QUIT, say) is a
send. So a person may, rarely, miss a digest, but never gets one every
hour.
Only one digest run goes at a
time (`app/jobs.py`, `_digest_lock`): a catch-up that comes while the
scheduled run is still sending (a start just before Monday 09:00) waits for
it, then finds nothing missed. The very first start with this version
records the latest periods as done, so nothing old goes out. The
other jobs bring things up to date each time they run, so a missed run is
done by the next one (the library and plays within minutes of a start, the
daily ones the next night). A job still running when its next turn comes
skips that turn; a digest run late (the process busy) still runs within the
hour (`misfire_grace_time`).
